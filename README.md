# fastapi-bookshop

## Быстрый старт

Если проект уже запускался до добавления постоянных томов Redis/RabbitMQ,
сначала выполните [однократный переход](#однократный-переход-с-прежней-конфигурации).

```bash
cp .env.example .env   # заполнить секреты (пароли, ключи Stripe/OAuth/LLM)
# положить JWT-ключи в ./cert (jwt-private.pem, jwt-public.pem)
docker compose up --build
```

Приложение: http://127.0.0.1:8000. Инфраструктурные порты (postgres 5432,
elasticsearch 9200, qdrant 6333, rabbitmq 5672/15672) слушают только 127.0.0.1.

После изменения зависимостей (`pyproject.toml` / `poetry.lock`):

```bash
docker compose up --build
```

`.venv` живёт внутри образа (в контейнеры монтируется только код), поэтому
пересборка образа сразу обновляет зависимости во всех сервисах.

## Контроль места на диске Docker

### Однократный переход с прежней конфигурации

Перед первым `up` с обновлённым Compose, пока старые контейнеры ещё существуют
(могут быть остановлены), выполните:

```bash
python3 scripts/adopt_docker_volumes.py
```

В Windows с установленным Python используйте `py scripts/adopt_docker_volumes.py`.
Скрипт создаёт локальный `docker-compose.override.yml`: закрепляет существующие
тома Redis/RabbitMQ и прежнее имя узла RabbitMQ. Данные не копируются и не удаляются.
Compose автоматически читает этот файл при последующих `up`/`down`.
Не удаляйте его и не переносите на другой компьютер: имена томов локальны.
Если override уже существует, скрипт останавливается без изменений — настройки
нужно объединить вручную. Если контейнеры уже удалены через `down`, скрипт не может
определить их прежние анонимные тома; для восстановления нужны их точные имена и
прежнее имя узла RabbitMQ. Для новой установки скрипт ничего не меняет.

### Обычная работа

```bash
docker compose up -d
docker compose stop
# продолжение работы с теми же контейнерами:
docker compose start
```

`docker compose down` тоже допустим: постоянные тома сохраняются. Теперь Redis и
RabbitMQ повторно используют свои тома, как PostgreSQL, Elasticsearch и Qdrant.
При необходимости пересоздать контейнеры и применить настройки: `docker compose up -d`.
Пересборка нужна после изменения Dockerfile или зависимостей, а не после сна
или перезагрузки. Код приложения уже смонтирован с хоста.

Во всех десяти dev-сервисах задан драйвер логов `local`: до трёх файлов примерно
по 10 МБ с ротацией и сжатием. Это ограничивает stdout/stderr, но не размер БД.
Применяется при пересоздании контейнеров; `start` настройки не обновляет.

### Ограничение кэша сборок — отдельно на каждом компьютере

Compose не управляет бюджетом BuildKit. В Docker Desktop откройте
**Settings → Docker Engine**, объедините содержимое
[`docs/docker-engine.json`](docs/docker-engine.json) с существующим JSON и нажмите
**Apply & restart**. Сохраните остальные параметры; пример задаёт явный
`builder.gc.policy` с бюджетом 2 ГБ вместо прежних политик сборки мусора.
Используйте актуальный Docker Engine (28+) с поддержкой `reservedSpace`.

Для OrbStack на Mac: `orb config docker`, добавьте тот же блок `builder.gc` и
сохраните файл — команда перезапустит Docker Engine. Перед этим остановите контейнеры.
Это общая настройка сборщика Docker для всех проектов на компьютере.

Проверьте `docker buildx inspect`: активная GC-политика должна показывать
`Reserved Space` около 2 GiB. В OrbStack одного `defaultKeepStorage`
может быть недостаточно из-за встроенных политик; поэтому пример содержит
явный `policy`. При необходимости примените его через `orb restart docker`.

Эта конфигурация включает периодическую сборку мусора с небольшим бюджетом.
Это не жёсткая квота всего Docker: используемые слои образов, активные сборки,
тома и логи учитываются отдельно; во время сборки возможен временный рост.
Меньший кэш означает, что некоторые следующие сборки будут дольше.

### Проверка и разовая очистка кэша

```bash
docker system df
docker buildx du
# Для современного Buildx: убрать восстанавливаемый кэш с небольшим резервом.
docker buildx prune --force --reserved-space 1GB --max-used-space 2GB
docker system df
```

Команда относится к выбранному сборщику, включая другие проекты. Она не удаляет
тома БД, контейнеры или теги образов. Если версия Buildx не поддерживает эти флаги,
`docker builder prune` предлагает интерактивное удаление неиспользуемого кэша.
Возрастной фильтр `until` может не освободить старые слои, если они зависят от
недавно использованных записей кэша.

`down`, сон и выключение компьютера не очищают кэш, образы и постоянные тома.
Размеры образов нельзя просто складывать: у них есть общие слои.
Не используйте `down -v` или очистку томов для борьбы с кэшем — там данные проекта.
Удаление старых анонимных томов требует отдельной проверки их содержимого.

В Windows место внутри виртуального диска Docker/WSL и размер его файла на
хосте могут уменьшаться не одновременно. Сначала сверяйте `docker system df`;
если там места уже мало занято, а файл VHDX остаётся большим, это отдельный вопрос
освобождения места виртуального диска, а не повторное накопление кэша.

Документация: [сборка мусора BuildKit](https://docs.docker.com/build/cache/garbage-collection/),
[хранение томов после down](https://docs.docker.com/reference/cli/docker/compose/down/),
[ротация local-логов](https://docs.docker.com/engine/logging/drivers/local/).
